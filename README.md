# Tilliworld Shop

Каталог предметов и заявки для Minecraft-сервера Tilliworld (1.16.5). React 19 + Vite + Tailwind CSS v4 + Supabase. Предметы покупаются за внутренние монеты сайта (миграции 009–010); **реальных платежей и автоматической выдачи в игре нет** — покупка создаёт заказ, предмет выдаёт администратор вручную.

## 1. Требования
Node.js 20+, аккаунт Supabase (бесплатного плана достаточно), аккаунт Vercel (по желанию).

## 2–3. Установка и запуск
```
npm install
npm run dev        # разработка
npm run check      # линтер + тесты + production-сборка
```
Отдельно: `npm run lint`, `npm test`, `npm run build`.

Без `.env` сайт работает в **демо-режиме**: тестовые предметы, заявки не сохраняются, админка показывает инструкцию.

## 4–6. Supabase
1. Создайте проект на supabase.com.
2. SQL Editor → выполните по порядку `supabase/migrations/001_init.sql`, `002_storage_and_hardening.sql`, затем `003_server_status.sql` (статус сервера), затем `004_reviews_mutes_audit.sql` (отзывы, подтверждение Minecraft, ответы, жалобы, муты, журнал) `006_player_accounts.sql` (аккаунты игроков по нику и паролю, без Supabase Auth и почты) `007_admin_accounts.sql` (управление аккаунтами игроков для администраторов) `008_manual_approval.sql` (ручное подтверждение регистрации) и `009_economy.sql` (монеты сайта и колесо удачи) и `010_shop_purchases.sql` (покупка предметов за монеты). Вторая миграция создаёт bucket `product-images` для изображений предметов с политиками доступа, запрещает администратору менять в заявке что-либо кроме статуса и разрешает в `image_url` только `https://`.
3. (Необязательно) для тестовых предметов выполните `supabase/seed_demo.sql`. Это тестовые данные, удалите их перед запуском.
4. Скопируйте `.env.example` в `.env` (файл `.env` в git не попадает) и заполните `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (Project Settings → API, ключ **anon/public** или **publishable**, он публичный по замыслу Supabase). `service_role`/secret-ключ в проект не добавляйте. В `.env.example` реальных значений быть не должно.

## 7. Первый администратор
Регистрации администраторов на сайте нет.
1. Supabase → Authentication → Users → Add user (почта + пароль, отметьте Auto Confirm).
2. SQL Editor:
```sql
update auth.users
set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"admin"}'
where email = 'ВАША_ПОЧТА';
```
`app_metadata` пользователь изменить не может. Войдите на `/admin` (после смены роли выйдите и войдите заново, чтобы обновился токен). Публичную регистрацию в Supabase Auth можно оставить выключенной («Allow new users to sign up»): игроки регистрируются не через неё, а через функции базы (миграция 006).

## 7а-1. Экономика сайта и колесо удачи (миграция 009)
Отдельные виртуальные монеты сайта: **не связаны с EssentialsX, Vault и игровым балансом Minecraft**, автоматической выдачи привилегий и реальных платежей нет.
- **Баланс**: таблица `player_balances` (создаётся с `0` триггером при создании аккаунта; для существующих аккаунтов создаётся миграцией). `CHECK` запрещает отрицательное значение и переполнение (максимум 10¹² монет). Игрок видит баланс в шапке, в «Аккаунте» и на странице `/wheel`.
- **Единственная точка изменения баланса** — внутренняя функция `economy_apply()`: блокирует строку баланса (`FOR UPDATE`), проверяет границы, пишет запись в журнал `economy_transactions` и меняет баланс в одной транзакции. Клиентам (`anon`/`authenticated`) доступ к таблицам и к этой функции закрыт, изменить баланс через frontend или API нельзя. Журнал неизменяем (триггеры запрещают UPDATE/DELETE/TRUNCATE) и переживает удаление аккаунта.
- **Колесо удачи**: `wheel_spin()` — один спин в 24 часа (по серверному времени), приз выбирается на сервере криптографически стойким `gen_random_bytes` (4 байта с отбрасыванием «хвоста», без смещения) ДО анимации; сайт только показывает готовый результат. Параллельные запросы одного игрока выстраиваются в очередь на блокировке баланса: успешен ровно один. История спинов (`wheel_spins`) хранит игрока, время, приз, статус и ссылку на транзакцию.
- **Призы по умолчанию**: 50 (35%), 100 (25%), 250 (20%), 500 (12%), 1000 (7%), 2500 (1%). Вероятности хранятся в сотых долях процента и обязаны давать ровно 100,00%; от 2 до 12 призов.
- **Админ-панель** `/admin/economy` (право `economy`; администраторы без ключа `permissions` имеют полный доступ, остальным добавьте `"economy"` в `app_metadata.permissions`): игроки и балансы с поиском, начисление/списание с обязательной причиной (минус — списание; ниже нуля уйти нельзя), журнал операций, включение/отключение колеса, редактор призов и вероятностей (с проверкой суммы), история спинов и статистика. Все проверки прав выполняет база, а не интерфейс.
- **Защита от CSRF**: сайт не использует cookie для авторизации. Игрок передаёт случайный токен в заголовке `x-player-token`, администратор — JWT в заголовке `Authorization`; браузер не добавляет их к чужим запросам, поэтому межсайтовая подделка запроса неприменима. Входные данные проверяются в функциях (типы, диапазоны, длина причины), SQL-инъекции исключены (параметризованные вызовы RPC).
- **Для будущего магазина**: покупка должна вызывать внутри своей SQL-функции `economy_apply(игрок, -цена, 'purchase', 'Название товара', 'shop_order', id_заказа)`. Виды операций `purchase` и `refund` в журнале уже предусмотрены, отдельной системы баланса не потребуется.

## 7а-2. Покупка предметов за монеты (миграция 010)
Применять после 009; повторный запуск безопасен, существующие предметы, заявки и балансы не меняются. Новых таблиц пользователей, баланса и товаров нет: используются `player_accounts`, `player_balances`/`economy_transactions` и `products`/`orders`.
- **Цена и правила** (поля `products`): `price_coins` (пусто — предмет не продаётся за монеты и остаётся обычной заявкой без оплаты), `purchase_mode` (`repeatable` — многоразовый, `one_time` — один раз на аккаунт), `max_per_player` (лимит покупок многоразового), `repurchase_cooldown_hours` (пауза между покупками). Задаются в `/admin/products`. Отклонённые заказы (монеты возвращены) в лимиты не засчитываются.
- **Покупка** — только функция `shop_purchase(товар, request_id, ожидаемая_цена)`. Цена, баланс и правила берутся из базы; клиент передаёт лишь товар, ключ попытки и цену, которую видел игрок (если цена успела измениться, покупка отклоняется с `price_changed`, а не списывает больше показанного). Списание (`economy_apply`, вид `purchase`) и создание заказа происходят в одной транзакции; при нехватке монет (`insufficient_funds`) не меняется ничего.
- **Защита от двойной покупки**: кнопка блокируется на время запроса; `request_id` (UUID попытки) уникален на игрока, поэтому повторная отправка (двойной клик, повтор после обрыва связи) возвращает уже созданный заказ и не списывает монеты второй раз. Покупки одного игрока сериализуются блокировкой его баланса: параллельные запросы не обходят ни баланс, ни правила одноразовости/лимита/паузы (проверено тестами).
- **Выдача предметов**: сайт и игровой сервер не связаны (плагин `minecraft-plugin/` только подтверждает Minecraft-ник), поэтому покупка создаёт заказ со статусом «Новая» = «ожидает выдачи». Ник для выдачи — подтверждённый Minecraft-ник, если аккаунт привязан, иначе логин аккаунта (в админке помечается «не подтверждён»). Администратор выдаёт предмет в игре вручную и ставит заказу «Выполнена»; только после этого игрок видит «Выдан (подтверждено администратором)». Автоматическая выдача потребует расширения плагина (получение выполненных заказов по ключу плагина и отметка о выдаче) и в эту миграцию не входит.
- **Возврат**: статус «Отклонена» у оплаченного заказа автоматически возвращает монеты (вид `refund`, ровно один раз, в той же транзакции). Вернуть возвращённый заказ в работу нельзя. Обычные заявки на товары с ценой отклоняются (`priced_product`), чтобы платный предмет нельзя было заказать бесплатно; товары без цены работают как прежде.
- **Права**: у `anon`/`authenticated` нет прямого доступа к балансу, журналу и заказам; админ в заказе по-прежнему может менять только статус (новые поля защищены триггером). Игрок читает свои покупки через `shop_my_orders()` и `shop_my_purchases()`.
- **Тесты**: `supabase/tests/010_shop_tests.sql` (psql, 66 проверок) и `supabase/tests/010_shop_concurrency.sh` (параллельные запросы), см. `supabase/tests/README.md`.

## 7а. Ручное подтверждение регистрации (миграция 008)
По умолчанию регистрация мгновенная (ник и пароль), а при первом заходе на сайт показывается форма регистрации. Ручное подтверждение включается командой `update public.registration_settings set require_approval = true;` (выключается `= false`). Когда оно включено, новый аккаунт создаётся в статусе «ожидает подтверждения» и войти не может, пока администратор с правом `accounts` не нажмёт «Одобрить регистрацию» в `/admin/accounts` (фильтр «Ожидают подтверждения», счётчик на вкладке). Отклонение требует причину: игрок увидит её при входе, ник остаётся занятым; позже заявку можно одобрить. Все аккаунты, созданные до миграции, считаются одобренными. Действия пишутся в журнал. Не более 500 заявок в ожидании одновременно.

## 7б. Отзывы, подтверждение Minecraft, муты, аккаунты (миграции 004, 006, 007)
**Регистрация игроков: только ник и пароль, без почты и без Supabase Auth.** Ник — это логин (3–16 символов, латиница, цифры, `_`; регистр не важен, ники уникальны), пароль от 8 символов. Аккаунты хранятся в таблице `player_accounts` (пароль — bcrypt через pgcrypto). После входа база выдаёт случайный токен; в таблице хранится только его sha256, а сайт отправляет токен в заголовке `x-player-token`, по нему функция `player_uid()` находит игрока. Клиент не передаёт ни роль, ни id. Аккаунты игроков и администраторов не пересекаются: администраторы входят на `/admin` через Supabase Auth (`app_metadata.role`), игрок не может получить их права. Сессия живёт 30 дней, не больше 5 сессий на аккаунт; после 10 неудачных входов подряд вход по этому нику блокируется на 15 минут. Ограничения: пароль нельзя восстановить по почте (можно только создать новый аккаунт либо владелец меняет хэш в базе); ник сам по себе ничего не доказывает, а значок «Подтверждён» даёт только проверка в игре; миграция 006 удаляет данные игроков, созданных ранее через Supabase Auth (отзывы остаются как «старые»). Миграция 005, если вы её применяли, снимается автоматически.


**Роли и права.** Вторая система администраторов не создавалась: роль по-прежнему `app_metadata.role = 'admin'`. Необязательно можно ограничить права конкретного администратора ключом `permissions` (список `moderate`, `mutes`, `audit`, `accounts`, `economy`, `shop` или `all`). Если ключа нет, права полные (как у ранее созданных администраторов):
```sql
update auth.users
set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"admin","permissions":["moderate"]}'
where email = 'ПОЧТА_МОДЕРАТОРА';
```
`moderate`: отзывы, ответы, жалобы; `mutes`: выдача и снятие мутов, поиск игроков; `audit`: журнал наказаний; `accounts`: сброс пароля, завершение сессий, отвязка Minecraft и удаление аккаунтов игроков, журнал этих действий (просматривать список и карточку аккаунта могут также `mutes` и `moderate`). После смены прав администратор должен перезайти. Ответ может изменить только его автор; удалить чужой ответ может администратор без ограничений.

**Аккаунты игроков в админ-панели (вкладка «Аккаунты»).** Список всех игроков с фильтрами (все / подтверждённые / не подтверждённые / в муте), поиск по нику, Minecraft-нику, UUID и ID. В карточке: дата регистрации, последний вход и число сессий, статус и UUID Minecraft, отзыв, жалобы, история мутов и действий над аккаунтом. Действия (право `accounts`): сменить пароль (старый узнать нельзя, хэш не показывается и не передаётся в браузер; администратор задаёт или генерирует новый и передаёт игроку лично), завершить все сессии, отвязать Minecraft, удалить аккаунт (нужно ввести ник; отзыв по выбору удаляется или остаётся как «старый»), выдать мут. Все действия пишутся в неизменяемый журнал `account_actions` (виден по праву `accounts` или `audit`), записи остаются и после удаления аккаунта. Старый адрес `/admin/players` перенаправляет на `/admin/accounts`.

**Подтверждение Minecraft-аккаунта (нужна установка плагина).**
1. Сайт выдаёт вошедшему игроку одноразовый код (10 минут, в базе только его sha256).
2. Игрок заходит на сервер под своим аккаунтом и вводит `/tilliverify КОД`.
3. Плагин `minecraft-plugin/` отправляет в SQL-функцию `confirm_minecraft_link` код, **ник и UUID из объекта игрока** и секрет плагина. Один Minecraft-аккаунт можно привязать только к одному аккаунту сайта.
4. Значок «Подтверждён» показывает сервер (по таблице `minecraft_links`). Введённый ник доказательством не считается.

Настройка:
1. Сгенерируйте секрет (минимум 32 символа), например `openssl rand -hex 32`, и внесите его **хэш**:
```sql
insert into minecraft_plugin_keys (label, key_hash) values ('main', sha256(convert_to('ВАШ_СЕКРЕТ', 'UTF8')));
```
Отозвать ключ: `update minecraft_plugin_keys set revoked_at = now() where label = 'main';`
2. Соберите плагин: `cd minecraft-plugin && mvn package` (нужны JDK 8+ и Maven), jar будет в `target/`.
3. Положите jar в `plugins/` сервера (Paper/Spigot 1.16.5), запустите сервер один раз и заполните `plugins/TilliVerify/config.yml`: `supabase-url`, `supabase-anon-key`, `plugin-secret`. Перезапустите сервер.
4. **Сервер должен работать с `online-mode=true`.** На сервере без лицензионной авторизации любой заходит под чужим ником, и подтверждение ничего не доказывает; плагин в этом режиме отключает проверку.
5. Секрет хранится только в `config.yml` сервера. В `.env` сайта и в клиентский код его помещать нельзя.

**Правила модерации.**
- Новый отзыв всегда уходит на модерацию (`pending`); статус задаёт только сервер. Один отзыв на аккаунт; ссылки запрещены; 10–1000 символов.
- Игрок может изменить свой отзыв, пока администратор его не скрыл. Любая правка возвращает отзыв на модерацию (нельзя одобрить одно и подменить текст). Удалить свой отзыв игрок может всегда, в том числе при муте.
- Ответ администрации виден только на опубликованном отзыве. Публично показывается имя, заданное в «Отзывы → Имя в публичных ответах» (по умолчанию «Администрация»), почта не публикуется.
- Муты: 10 минут, 1 час, 24 часа, 7 дней, навсегда; причина обязательна (3–500 символов). Срок считает база. Мут блокирует создание и правку отзывов (функция `assert_can_publish`, её обязана вызывать любая будущая функция публикации, например комментарии). Мут действует на аккаунт и на подтверждённый Minecraft UUID, поэтому не снимается отвязкой аккаунта. Нельзя замутить себя или администратора, игрок не может снять мут (снимает только администратор с правом `mutes`).
- Журнал `mute_audit` (выдача, истечение срока, снятие) только дополняется: UPDATE/DELETE/TRUNCATE блокируются триггером даже для владельца БД, внешних ключей на пользователей нет, поэтому записи переживают удаление аккаунта. Запись об истечении создаётся при ближайшем обращении к мутам (время события равно моменту окончания). Время хранится в UTC, на сайте показывается в часовом поясе пользователя.
- Мут на сайте никак не связан с наказаниями в Minecraft.

## 8. Edge Functions
Не используются. Заявки создаёт SQL-функция `create_order` (security definer): она проверяет ник, количество, комментарий, существование и доступность предмета и ограничивает частоту (3 заявки на ник и 60 на сайт в минуту). Прямого INSERT в `orders` у посетителей нет. Ограничение по IP в функции нет; если понадобится, добавьте Edge Function с секретами `supabase secrets set ...` (не в `.env`).

## 9. Vercel
Импортируйте репозиторий, добавьте две переменные `VITE_SUPABASE_*`, Build: `npm run build`, Output: `dist`. SPA-маршруты настроены в `vercel.json`.

## 10. Проверка безопасности (сделайте после настройки)
- Без входа: `select * from orders` через anon-ключ (REST) возвращает пусто/ошибку; `update orders` не проходит.
- Вошедший не-админ получает пустой список заявок и отказ на изменения.
- `/admin` без входа показывает только форму входа.
- Запрос `create_order` на скрытый/недоступный предмет возвращает `product_unavailable`.
- Роль в `user_metadata` не даёт прав: администратором считается только `app_metadata.role = 'admin'`.
- Даже администратор через API не может изменить ник, количество, комментарий или название в заявке (ошибка `orders_immutable_fields`), только статус.
- Загрузка в `product-images` без входа или от не-администратора отклоняется.
- Статус сервера: `update server_status set is_online = true` с anon-ключом или от вошедшего не-админа ничего не меняет.

## Изображения
В `/admin/products` изображение можно загрузить файлом или указать https-ссылку.
- Файлы уходят в Supabase Storage, bucket `product-images`. Формат: PNG, JPEG или WebP, размер до 2 МБ.
- Формат определяется по сигнатуре файла, а не по расширению. Имя файла заменяется случайным UUID.
- Ограничения продублированы на стороне Supabase: `file_size_limit` и `allowed_mime_types` у bucket. Записывать, менять и удалять файлы может только администратор (политики на `storage.objects` через `is_admin()`).
- Bucket публичный: файлы открываются по прямой ссылке, список файлов посетителям недоступен.
- При замене или удалении предмета старый файл удаляется из Storage.

## Статус сервера (включён / выключен)
В админке на странице «Обзор» (`/admin`) есть карточка «Статус Minecraft-сервера» с кнопкой переключения. Посетители видят статус на главной и в подвале сайта. Страница сама обновляет его раз в минуту и при возвращении на вкладку.
- Статус выставляется **вручную**: сайт сервер не опрашивает (Aternos засыпает без игроков, а подключение к серверу по ТЗ не реализуется). Переключайте, когда запускаете или останавливаете сервер.
- Хранится в таблице `server_status` (одна строка). Читать может любой, менять только администратор (RLS, миграция 003).
- Если миграция 003 не применена или строки нет, посетитель видит «Статус сервера не указан», а админка подсказывает выполнить миграцию. В демо-режиме показывается «не указан», ложного «включён» нет.

## Адреса предметов
`/shop/:id` принимает UUID или slug (например, `/shop/diamond-sword`). Неизвестный адрес показывает «Предмет не найден».

## Известные ограничения
- Лимит частоты заявок считается по нику и по сайту целиком, без учёта IP. Для ограничения по IP нужна Edge Function.
- В админке загружаются последние 500 заявок, постраничной загрузки нет.
- Production-бандл около 544 КБ (157 КБ gzip), из них около 200 КБ занимает `supabase-js`; Vite выводит предупреждение о размере чанка. Это не ошибка.
- Плагин `minecraft-plugin/` проверен только компиляцией против заглушек Bukkit API и его HTTP-часть вызвана против локального PostgREST. На реальном Paper/Spigot-сервере (и на Aternos: поддержка плагинов и исходящих HTTPS-запросов) не запускался.
- Мут привязан к аккаунту сайта и подтверждённому Minecraft UUID. Неподтверждённый игрок, замутённый на аккаунте, может зарегистрировать новый ник; это затрудняет только лимит регистраций (30 в минуту на сайт).
- Комментариев на сайте нет, поэтому проверка мута подключена к отзывам. Новую функцию публикации нужно начинать с `assert_can_publish(auth.uid())`.
- Имя подтверждённого игрока берётся из момента подтверждения; при смене ника в Minecraft нужно пройти проверку заново.
- Реальные регистрация и вход в Supabase Auth не проверялись: в стенде токены подписаны вручную, запрос регистрации перехвачен. В частности, не проверено, примет ли GoTrue служебный домен.

## Часть 2 — привилегии и управление выдачей

После применения миграции `supabase/migrations/011_privileges_and_fulfillment.sql` в админке товаров можно выбирать тип `Предмет` или `Привилегия`, задавать ключ выдачи и срок действия. Раздел `/privileges` показывает опубликованные привилегии. Покупка остаётся через `shop_purchase`: серверная функция использует цену из БД, блокировку баланса игрока и UUID идемпотентности; постоянные привилегии следует настроить как `one_time`. История покупок хранится в `orders`, а поля `fulfillment_status`, `fulfillment_attempts`, `fulfilled_at` и `fulfillment_note` фиксируют состояние выдачи.

**Важно:** существующий `minecraft-plugin` — плагин подтверждения привязки ника, а не обработчик выдачи привилегий. Поэтому автоматическая выдача здесь намеренно не имитируется: администратор должен фактически выдать привилегию в игре и только затем отметить заказ выполненным. Отклонение оплаченного заказа использует существующий атомарный механизм возврата. Для автоматической выдачи нужна отдельная серверная интеграция с аутентифицированной очередью/эндпоинтом и идемпотентным обработчиком на игровом сервере; секреты нельзя размещать в браузере.


## Часть 3 — безопасность магазина, безопасная выдача, проверка (миграция 012)

Применять после 011: `supabase/migrations/012_security_hardening.sql` (повторный запуск безопасен, данные не удаляются).

- **Новое право `shop`.** Запись в `products`, `orders` и Storage с изображениями раньше требовала только роль `admin`: администратор с ограниченными правами (например, только `moderate`) мог через REST менять цены и отклонять заказы (отклонение возвращает монеты). Теперь нужно право `shop`. Администраторы без ключа `permissions` и с `all` имеют его автоматически. **Ограниченным администраторам, которые работают с заказами и товарами, добавьте `"shop"` в `app_metadata.permissions`** (пример SQL в разделе 7б), иначе вкладки «Заявки» и «Предметы» перестанут работать для них. Чтение заявок осталось у любого администратора.
- **Выдача оплаченного заказа** идёт функцией `admin_fulfillment_step` (кнопки в карточке заказа): `start` (начать/повторить, попытка +1) → `fail` (ошибка, причина обязательна) → снова `start` либо `done` (выдано, статус «Выполнена»). Повтор `done` ничего не меняет. Поля `fulfillment_*` напрямую не меняются.
- **Возврат монет** — отклонение заказа (один раз, в одной транзакции со сменой статуса). Запрещён после выдачи (`order_fulfilled`) и во время выдачи (`order_processing`); из «Выполнена» вернуться в работу нельзя. Возвращённый заказ нельзя «воскресить» и выдать.
- **Выдача по-прежнему ручная**: сайт не связан с игровым сервером, плагин `minecraft-plugin` только подтверждает ник. Автовыдача привилегий не реализована.
